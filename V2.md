# Version 2.0 — mark tasks as done

Version 2.0 is a **separate release** on the `v2` branch, tagged `v2.0.0`. It
adds one small feature and one database change:

- a `done` boolean column on `tasks`,
- `PATCH /api/tasks/:id` to set `done` to `true` or `false`,
- a **Mark as done** button that strikes the task through,
- a safe migration that runs automatically on startup and keeps every existing
  row.

No new packages. Only `server/index.js`, `client/src/App.jsx`,
`client/src/index.css` and the documentation change.

| Version | Branch | Tag | API endpoints |
| ------- | ------ | --- | ------------- |
| 1.0.0 | `main` | `v1.0.0` | `GET`, `POST`, `DELETE` |
| 2.0.0 | `v2` | `v2.0.0` | `GET`, `POST`, `DELETE`, **`PATCH`** |

## 2. The migration

```sql
-- Add one column. Existing rows are kept and get done = false.
ALTER TABLE tasks ADD COLUMN IF NOT EXISTS done BOOLEAN NOT NULL DEFAULT FALSE;
```

### Why this is safe

| Property | Why it matters |
| -------- | -------------- |
| **Only `ADD COLUMN`** | Nothing is dropped or renamed, so no row is lost. |
| **`NOT NULL DEFAULT FALSE`** | Every existing row gets a valid value (`false`) immediately; no backfill script is needed. |
| **`IF NOT EXISTS`** | Running it twice is harmless. Startup code can safely run it on every boot. |
| **Old code still works** | Version 1 selects `id, title, created_at` only, so it simply ignores the extra `done` column. Rolling the code back to v1 does not break. |
| **No table lock for long** | The table is tiny in this demo. On a huge table, adding a `NOT NULL DEFAULT` column can lock it while rows are filled — a real-warning to mention. |

You do **not** have to run it by hand. `server/index.js` on `v2` runs, on every
start, in this order:

1. `CREATE TABLE IF NOT EXISTS tasks (...)` — creates the table on a brand-new
   database (this already includes `done`).
2. `ALTER TABLE tasks ADD COLUMN IF NOT EXISTS done ...` — upgrades an existing
   version 1 database.

```js
await pool.query(`
  CREATE TABLE IF NOT EXISTS tasks (
    id SERIAL PRIMARY KEY,
    title TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    done BOOLEAN NOT NULL DEFAULT FALSE
  )
`);

// Version 1 databases already have a tasks table, so add the new column.
// Existing rows get done = false and no data is deleted.
await pool.query(
  'ALTER TABLE tasks ADD COLUMN IF NOT EXISTS done BOOLEAN NOT NULL DEFAULT FALSE'
);
```

### Run it by hand (optional, for the demo)

On Render, use the **External Database URL** from the database's **Connections**
tab (the internal one only works from inside Render):

```bash
psql "postgres://USER:PASSWORD@HOST:5432/tasktracker" \
  -c "ALTER TABLE tasks ADD COLUMN IF NOT EXISTS done BOOLEAN NOT NULL DEFAULT FALSE;"
```

Locally:

```bash
psql -U postgres -d tasktracker \
  -c "ALTER TABLE tasks ADD COLUMN IF NOT EXISTS done BOOLEAN NOT NULL DEFAULT FALSE;"
```

### `server/index.js`

```diff

-      'SELECT id, title, created_at FROM tasks ORDER BY id ASC'
+      'SELECT id, title, done, created_at FROM tasks ORDER BY id ASC'

 POST /api/tasks
-      'INSERT INTO tasks (title) VALUES ($1) RETURNING id, title, created_at',
+      'INSERT INTO tasks (title) VALUES ($1) RETURNING id, title, done, created_at',

 new route after DELETE /api/tasks/:id
+// PATCH /api/tasks/:id - mark a task done or not done. Body: { "done": true }
+app.patch('/api/tasks/:id', async (req, res) => {
+  const id = Number(req.params.id);
+  const { done } = req.body;
+
+  if (!Number.isInteger(id) || id < 1) {
+    return res.status(400).json({ error: 'Invalid task id' });
+  }
+
+  if (typeof done !== 'boolean') {
+    return res.status(400).json({ error: 'done must be true or false' });
+  }
+
+  try {
+    const result = await pool.query(
+      'UPDATE tasks SET done = $1 WHERE id = $2 RETURNING id, title, done, created_at',
+      [done, id]
+    );
+
+    if (result.rowCount === 0) {
+      return res.status(404).json({ error: 'Task not found' });
+    }
+
+    res.json(result.rows[0]);
+  } catch (err) {
+    console.error('PATCH /api/tasks/:id failed:', err.message);
+    res.status(500).json({ error: 'Could not update task' });
+  }
+});
```

The `PATCH` route is placed with the other API routes, **before** the
`app.get('*')` catch-all that serves React.

## 4. Test the API with curl

```bash
# Add a task
curl -X POST http://localhost:3000/api/tasks \
  -H "Content-Type: application/json" \
  -d '{"title":"Test v2"}'

# Mark it done (use the id returned above)
curl -X PATCH http://localhost:3000/api/tasks/1 \
  -H "Content-Type: application/json" \
  -d '{"done":true}'

# Mark it not done
curl -X PATCH http://localhost:3000/api/tasks/1 \
  -H "Content-Type: application/json" \
  -d '{"done":false}'
```

A successful PATCH returns the updated task:

```json
{
  "id": 1,
  "title": "Test v2",
  "done": true,
  "created_at": "2026-11-27T09:44:50.349Z"
}
```

Error cases: `PATCH /api/tasks/abc` → `400 Invalid task id`;
`PATCH /api/tasks/9999` → `404 Task not found`;
`PATCH` with `{"done":"yes"}` → `400 done must be true or false`.

## 6. Rollback notes

Rollback is a **release-management** action: you deploy the previous version
again. Our V2 is designed so that this is easy.

### Option A — Render, no code change

Dashboard → the service → **Deploys** → find the last good deploy →
**⋯ → Redeploy this deploy**. The old build (v1) starts again.

### Option B — git revert, then push

```bash
git log --oneline            # find the merge or commit that released v2
git revert -m 1 <merge-hash> # or: git revert <commit-hash>
git push origin main
```

Render deploys the revert. The v1 code runs against the v2 database.

### Why this rollback is safe

- The migration **only added** a column. Nothing was dropped, so no data is
  missing when old code reads the table.
- v1's queries name their columns (`id, title, created_at`), so the extra
  `done` column is simply ignored.
- The `tasks` rows, including titles and timestamps, are unchanged.
- Rolling forward again (redeploy v2) is also safe, because `ADD COLUMN IF NOT
  EXISTS` does nothing the second time.

### What would make rollback hard

- Dropping or renaming a column, or changing a type, **destroys or rewrites**
  data. Old code then breaks or reads wrong values.
- A data migration that transforms rows (for example, splitting `title` into
  two columns) is hard to undo without a backup.
- Therefore: **take a backup / snapshot before a destructive database change**,
  and prefer additive migrations.

### Verify the rollback

1. Render deploy is **Live**.
2. Page loads and the old tasks are still listed.
3. **No** "Mark as done" button (v1 UI).
4. Adding a task still works and survives a refresh.
5. Logs contain no errors.
