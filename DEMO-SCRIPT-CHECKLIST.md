# Live demo script — click, say, expect

**Group 6 · WST2 Lesson 4 · Web Application Deployment and Release Management**

Numbers are steps, not minutes. `[CLICK]` = mouse action, `[SAY]` = the sentence
to say, `[EXPECT]` = what the audience must see. Keep this file open on a second
monitor or phone.

- [ ] Tabs open in this order: **1)** GitHub repo, **2)** Render dashboard
      (service), **3)** Render PostgreSQL (Connections tab), **4)** the live
      app, **5)** this script.
- [ ] Terminal open in the project folder, font large.
- [ ] `git status` is clean and `git log --oneline -3` shows the release commits.
- [ ] `git tag` shows `v1.0.0` and `v2.0.0`.
- [ ] The live URL loads and one test task is already in the list (delete it

- [ ] Backup folder open: `demo-backup/` with the screenshots from step 15.

## 1. Show the source files

- [CLICK] Open the repo, then `server/index.js`.
- [SAY] "This is the whole backend — Express serves the API and the built React
  files. At the top it reads `DATABASE_URL`; if it is missing it prints
  `DATABASE_URL is not defined` and exits with status 1."
- [CLICK] Scroll to the routes: `GET /api/tasks`, `POST /api/tasks`,
  `DELETE /api/tasks/:id`.
- [SAY] "Three routes: list, add, delete. SQL uses `$1` placeholders so user
  text can never be executed as SQL."
- [CLICK] Scroll to the bottom: `CREATE TABLE IF NOT EXISTS tasks`.
- [SAY] "The server creates the table on startup, so the first deploy needs no
  manual SQL."
- [CLICK] Open `client/src/App.jsx`.
- [SAY] "This is the only page. It loads tasks from `/api/tasks` and sends POST
  and DELETE. No TypeScript, no ORM, no auth — on purpose."
- [CLICK] Open `package.json`.
- [SAY] "Two scripts matter: `build` installs and builds the React client into
  `client/dist`; `start` runs `node server/index.js`."

## 2. Show what is NOT uploaded

- [CLICK] Open `.gitignore`.
- [SAY] "Three things are excluded. `node_modules` is huge and is rebuilt by
  `npm install`. `.env` holds the real database password. `client/dist` is
  generated by the build."
- [CLICK] Open `.env.example`.
- [SAY] "The repo only contains example values. Never commit a real URL."

## 3. Prove the build

- [CLICK] Terminal: `npm run build`
- [EXPECT] `✓ built in ...`, and a `dist/assets/` line.
- [CLICK] `ls client/dist` then `ls client/dist/assets`
- [SAY] "Build turned React into plain static files: one HTML, one JS, one CSS.
  This folder is what Express will serve in production."
- [SAY] "Fast-forward: the same command runs on Render. A build is just files —
  it does not need a database."

## 4. Explain the flow

- [CLICK] Point at the README diagram, or draw on the board:

```
laptop (localhost) --git push--> GitHub --webhook--> Render build+run --> public URL
```

- [SAY] "We develop on the laptop, push to GitHub, Render builds and runs it, and
  users open a public URL. Nothing runs on the laptop during the demo."

## 5. Render: database FIRST

- [CLICK] Render → **New → Postgres**.
- [SAY] "Database first, because the web service needs its URL. If we create the
  web service first we would have nothing to paste."
- [CLICK] Show name, region, free plan → **Create**.
- [CLICK] After it is **Available**, open **Connections** → copy **Internal
  Database URL**.
- [SAY] "Internal URL is private and fast and only works inside Render. We use it
  because both services are in Render. Keep the same region."
- [EXPECT] A URL starting with `postgres://` in the clipboard.

## 6. Render: web service

- [CLICK] **New → Web Service** → choose the repo.
- [CLICK] Name `task-tracker`; Language **Node**; Branch **main**.
- [SAY] "Branch `main` is version 1. Version 2 lives on `v2`."
- [CLICK] Build Command: `npm install && npm run build`.
- [SAY] "Install server packages, then install and build the client. That
  creates `client/dist` on Render's machine."
- [CLICK] Start Command: `npm start`.
- [SAY] "That is `node server/index.js`, the same command we ran locally."
- [CLICK] Instance type **Free**, Auto-Deploy **Yes**.

## 7. Environment + verify SSL

- [CLICK] **Environment** → add `DATABASE_URL` = the Internal URL.
- [SAY] "This is the only secret. It lives in Render's settings, never in git."
- [CLICK] Look through the variable list for `NODE_ENV`.
- [SAY] "SSL is on when `NODE_ENV=production`. I will not assume Render sets it,
  so if it is not listed I add `DATABASE_SSL=true`."
- [SAY] "Do not set PORT — Render injects it and the code reads
  `process.env.PORT`."
- [CLICK] **Create Web Service**.

## 8. Read the deploy log out loud

- [CLICK] **Logs**.
- [EXPECT] `Build successful`, then:
  `Connected to PostgreSQL; table "tasks" is ready.`
  and `Task Tracker server running on http://localhost:10000`.
- [SAY] "Build success means the files were produced. The second line means the
  app reached PostgreSQL and created the table. Two different proofs."
- [SAY] "Localhost in the log is just a message; Render exposes it on the public
  URL."

## 9. Verify on the public URL

- [CLICK] Open `https://task-tracker.onrender.com`.
- [SAY] "Check 1: the page loads — the build was served correctly."
- [CLICK] Type "Demo task", click **Add**.
- [SAY] "Check 2: the task appears — POST reached the API."
- [CLICK] Press **F5**.
- [SAY] "Check 3: it is still there. That is the proof the data is in PostgreSQL,
  not just in React's memory."
- [CLICK] Render → **Logs**.
- [SAY] "Check 4: no errors in the log."

## 10. Break demo A — delete `DATABASE_URL`

- [SAY] "Now a deliberate mistake: I delete the database URL."
- [CLICK] **Environment** → delete `DATABASE_URL` → **Save, rebuild, deploy**.
- [CLICK] Open the new deploy's **Logs**, scroll to the bottom.
- [EXPECT]
  ```text
  ==> Running 'npm start'
  DATABASE_URL is not defined
  Set it in .env locally, or in the Render Environment tab.
  ==> Exited with status 1
  ```
- [SAY] "Notice the build succeeded. Config errors are not build errors — the
  app only needs the database when it starts. The guard at the top of the file
  prints one clear line and exits 1."
- [CLICK] Re-add `DATABASE_URL` with the Internal URL → **Save and deploy**.
- [EXPECT] The two healthy log lines again; tasks are still there.
- [SAY] "The database was never touched, so the data survived. Only the
  configuration was broken."

## 11. Break demo B — remove `pg`

- [CLICK] Open `package.json` on GitHub (or in the editor), delete
  `"pg": "^8.13.1"`.
- [CLICK] Delete only in the `dependencies` block, leaving valid JSON.
- [SAY] "I remove the PostgreSQL driver, then commit and push."
- [CLICK] `git add package.json && git commit -m "Demo: remove pg" && git push`
- [CLICK] Render → newest deploy → **Logs** → search `Cannot find module`.
- [EXPECT]
  ```text
  Error: Cannot find module 'pg'
  Require stack:
  - /opt/render/project/src/server/index.js
      at Object.<anonymous> (/opt/render/project/src/server/index.js:15:18)
  ...
  ==> Exited with status 1
  ```
- [SAY] "Line 15 is `require('pg')`. The build passed because the build never
  runs the server. The crash happens at start, which is why the log is the first
  place to look."
- [CLICK] Fix:
  `npm install pg && git add package.json package-lock.json && git commit -m "Restore pg" && git push`
- [EXPECT] Healthy start; data still there.

## 12. Release management — version 2.0

- [CLICK] Terminal: `git branch` → `main`, `v2`. `git tag` → `v1.0.0`,
  `v2.0.0`.
- [SAY] "`MAJOR.MINOR.PATCH`: 2.0.0 is a feature plus a database change; 1.0.1
  would just be a patch."
- [CLICK] `git show v2.0.0:server/index.js | grep -n "ALTER TABLE"`
- [SAY] "The release is a tagged commit, so we can always deploy exactly that
  code again."
- [CLICK] Merge/redeploy v2 (or switch the branch in Settings → Build & Deploy).
- [EXPECT] The new deploy is **Live**, old tasks still listed and **not** struck
  through; a **Mark as done** button is visible.
- [CLICK] Mark a task done → refresh.
- [SAY] "PATCH persisted. The migration added `done` with a default `false`, so
  every old row kept its data."

## 13. Rollback

- [CLICK] Render → **Deploys** → previous deploy → **⋯ → Redeploy**.
- [SAY] "Rollback option A: redeploy the previous build. Seconds, no code."
- [SAY] "Option B is `git revert <commit>` and push. Slower but visible in the
  history."
- [SAY] "Warning: rollback is easy for code, hard for databases. Our migration
  only added a column, so v1 code ignores it and still works. If we had dropped
  a column, the data would be gone."
- [CLICK] Reload the app: no strike-through button, tasks still there.
- [CLICK] Redeploy v2 again (roll forward).

## 14. Deployment strategies (talk, do not fake)

- [CLICK] Show the diagrams in README section 8.
- [SAY] "Render's free plan is one instance, so we simulate these. We are not
  splitting real traffic."
- [SAY] "Rolling: replace instances one at a time. No downtime, no extra
  servers, but two versions run together for a while."
- [SAY] "Blue-green: two complete environments, switch the router. Instant
  rollback, but double the cost."
- [SAY] "Canary: 5% of users get v2, watch the metrics, then increase. Small
  blast radius, but needs traffic control and monitoring."
- [SAY] "Difference in one line: rolling replaces machines, blue-green switches
  everything at once, canary splits traffic by percentage."

## 15. Final checklist + close

- [CLICK] The live URL again: page loads, add a task, refresh, still there.
- [CLICK] Logs: no errors, newest deploy **Live** and commit matches GitHub.
- [SAY] "Five checks: page loads, task appears, survives refresh, logs clean,
  and for v2 the done state persists. Each one proves a different layer."
- [SAY] "That is deployment: build once, ship the same build, verify, then
  release and roll back safely."

**Fallback 2 — recorded video.** A 3–5 minute screen recording of the full flow
(local build → deploy → both breaks → release → rollback). Play it muted while
you narrate live. Keep it on the laptop, not only in the cloud.

**Fallback 3 — same app locally.** No internet at all:

```bash
npm run build
npm start          # needs local PostgreSQL and .env
```

Open <http://localhost:3000>. You can still show add/refresh persistence and the
two error messages by hiding `.env` and by moving `node_modules/pg`. Say clearly:
"This is the same code and the same commands, running locally instead of on
Render."

**Phone hotspot.** If only the campus Wi-Fi is down, tether and retry the Render
URL — the deployed service does not depend on the campus network.

**Do not** try to re-create the whole Render service live if it is deleted;
switch to the screenshots and keep the explanation going.
